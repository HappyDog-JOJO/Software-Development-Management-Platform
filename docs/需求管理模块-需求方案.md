## 一、总体定位与菜单结构

与「售后问题」并列的独立业务线,共用现有用户 / 部门 / 字典 / 附件上传 / 站内消息 / 操作日志基础设施。侧边栏新增分组「开发管理」,按角色过滤:

```
开发管理
├── 需求提交    （所有登录角色）
├── 我的需求    （所有登录角色：只看自己提交的，跟踪进度）
├── 评审池      （评审委员、管理员）
├── 需求池      （产品经理、评审委员、管理员）
├── 设计中心    （产品经理、评审委员、管理员）
├── 开发中心    （开发负责人、产品经理、评审委员、管理员）
└── 发布上线    （评审委员、管理员：执行发布动作）
```

## 二、角色扩展

在现有 4 角色(销售员、售后服务人员、销售经理、管理员)基础上新增 4 个:

| 角色 | 职责 | 对应环节 |
| --- | --- | --- |
| 评审委员 | 评审需求:通过 / 驳回(任一委员通过即生效);发布上线 | 评审池、发布上线 |
| 产品经理 | 从需求池挑选需求、上传设计文档、指定开发分支与开发负责人 | 需求池、设计中心 |
| 开发工程师 | 担任主任务开发负责人,负责按分支完成开发 | 开发中心 |
| 质量审核员 | (角色保留可分配;质量中心已下线,暂无专属环节) | — |

- 多角色并集机制不变(如一人可同时是「产品经理 + 评审委员」)。
- **管理员拥有所有环节的操作权(兜底)**;**发布动作由评审委员 / 管理员执行**。
- 角色字符串白名单需两端同步:后端 `site/inc/auth.php` 的 `qly_roles()` 与前端 `frontend/src/constants/user.ts` 的 `ROLES`。

## 三、主流程与状态机(主任务 = 需求单)

```
提交需求
    │
    ▼
┌────────┐  委员通过(任一)   ┌────────┐  PM认领   ┌────────┐
│ 评审池  │ ───────────────▶ │ 需求池  │ ────────▶ │ 设计中心 │
└───┬────┘                   └────────┘           └───┬────┘
    │ 委员驳回                                         │ PM上传设计文档
    ▼                                                 │ 定分支+开发负责人
┌────────┐                                            ▼
│ 已驳回  │（终态·作废，不可重提）        ┌────────┐ 提交开发完成(手动) ┌────────┐
└────────┘                              │ 开发中心 │ ──────────────────▶ │ 待发布  │
                                        └────────┘                     └───┬────┘
                                                                       │ 发布(评审委员/管理员)
                                                                       ▼
                                                                   ┌────────┐
                                                                   │ 已上线  │（终态）
                                                                   └────────┘
```

**主任务状态枚举**:`评审池 → 需求池 → 设计中心 → 开发中心 → 待发布 → 已上线`;终态 `已驳回`(评审驳回,作废,不可重提;如仍需要,重新提交一条新需求)、`已取消`(提交人撤回)。

**子任务功能已删除**(v1.3):开发负责人直接在开发中心提交开发完成(填完成说明+附件),主任务进入待发布。

## 四、各环节操作细则

| # | 环节 | 操作人 | 动作 | 必填内容 | 流转结果 |
| --- | --- | --- | --- | --- | --- |
| 1 | 需求提交 | 所有登录用户 | 提交 | 所属模块、优先级、需求描述(附件可选) | 进入评审池 |
| 2 | 评审池 | 评审委员、管理员 | 通过 | —(可附评审意见) | 进入需求池 |
| 3 | 评审池 | 评审委员、管理员 | 驳回 | 驳回原因(附件可选) | **状态=已驳回(终态·作废)**,通知提交人 |
| 4 | 评审池/需求池 | 提交人本人 | 取消 | — | 状态=已取消(终态) |
| 5 | 需求池 | 产品经理、管理员 | 认领 | — | 进入设计中心,锁定认领的 PM |
| 6 | 设计中心 | 认领的 PM | 完成设计 | 设计文档(附件,**必传**)、开发分支、开发负责人 | 进入开发中心 |
| 7 | 开发中心 | 开发负责人 | 提交开发完成 | 完成说明(**必填**,至少 5 字,附件可选) | **主任务进入待发布**,通知评审委员/管理员 |
| 8 | 发布上线 | 评审委员、管理员 | 执行发布 | —(可附上线说明) | 状态=已上线,终态 |

## 五、需求单字段(对齐「提交问题」页风格)

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 提交人 / 提交部门 | 自动 | 取当前登录人及其部门(无部门拦截提交,同问题提交) |
| 所属模块 | 必填 | 复用现有「模块」字典(下拉,仅启用项) |
| 优先级 | 必填 | **低 / 中 / 高 / 紧急**,默认「中」;需求池按优先级排序供 PM 挑选 |
| 需求标题 | 必填 | 列表/看板浏览刚需 |
| 需求描述 | 必填 | 至少 10 字(与问题提交一致) |
| 附件上传 | 可选 | 最多 9 个,复用现有上传接口 |

系统自动生成:需求编号(`XQ + 日期时间 + 随机`,同问题编号 WT 的生成方式)、各环节进入时间戳与经办人。

## 七、数据模型

### 表 `dev_request`(需求主任务)

- 基础:`id`、`req_no`(唯一)、`title`、`description`、`module_id`、`module_name`(快照)、`priority`(低/中/高/紧急,默认中)、`status`、`submitter_id/name/account`、`department_id`
- 评审:`reviewer_id/name`、`review_comment`、`reviewed_at`
- 设计:`pm_id/name`(认领 PM)、`design_doc`(设计说明,设计文档附件走附件表)、`branch`(开发分支)、`dev_leader_id/name`、`designed_at`
- 开发:`dev_done_note`(开发完成说明)、`dev_done_at`(开发完成时间)
- 发布:`released_at`(发布上线时间)、`released_by`(发布操作人)
- 时间:`created_at`、`updated_at`、各环节进入时间 `pool_at / design_at / battle_at / frontline_at(进入待发布)`
- 废弃(质量中心已下线,仅保留历史数据,不再写入):`inspector_id/name`、`inspect_result`、`inspect_comment`、`inspected_at`、`reject_count`、`inspect_at`

### 表 `dev_request_attachment`(附件)

`id`、`request_id`、`scene`(submit提交/design设计/reject驳回/done完成/release上线)、`url/name/size/mime_type`、`uploader_id`、`created_at`

### 复用

- 操作时间线:`operation_log` 新增类型 `提交需求 / 需求评审 / 需求设计 / 需求开发 / 需求发布`(`质量审核` 仅存量历史日志可能出现),详情页按需求编号过滤展示(同问题详情做法)。
- 站内消息:复用 `notification` 表与现有轮询弹窗机制,消息带跳转链接进需求详情。
- 字典:复用 `module`;附件上传复用 `upload` 接口。

## 八、消息通知矩阵(每个节点都不能漏)

| 事件 | 通知谁 | 内容要点 |
| --- | --- | --- |
| 提交需求(进评审池) | 全部评审委员 + 管理员 | 新需求待评审 |
| 评审通过(进需求池) | 提交人 + 全部产品经理 | 评审通过 / 需求池有新任务 |
| 评审驳回(作废) | 提交人 | 需求未通过评审,附驳回原因 |
| PM 认领(进设计中心) | 提交人 | 您的需求已进入设计阶段 |
| 设计完成(进开发中心) | 指定的开发负责人 | 新开发任务,附分支名 |
| 开发完成(进待发布) | 全部评审委员 + 管理员 | 需求开发完成,待发布上线 |
| 发布上线(终态) | 提交人 + 产品经理 + 开发负责人 | 您的需求已上线 |

所有通知带跳转链接,点击进入对应需求详情。

## 九、后端接口(api.php 新增路由,模式与 issues 一致)

```
devreqs             GET   需求列表（按环节/关键字/模块/优先级/只看我的筛选，按角色控可见范围）
devreqs/detail      GET   需求详情（含附件、时间线日志、开发完成信息）
devreqs/create      POST  提交需求（进评审池）
devreqs/cancel      POST  提交人取消（仅评审池/需求池阶段）
devreqs/review      POST  评审：通过/驳回（评审委员；驳回=作废终态）
devreqs/claim       POST  产品经理认领（需求池 → 设计中心）
devreqs/design      POST  完成设计：设计文档+分支+开发负责人（设计中心 → 开发中心）
devreqs/devdone     POST  提交开发完成：完成说明+附件（开发中心 → 待发布）
devreqs/release     POST  执行发布（评审委员/管理员；待发布 → 已上线）
```
