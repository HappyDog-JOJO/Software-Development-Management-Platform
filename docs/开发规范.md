# 售后服务平台 · 开发规范

> 版本:v1.1(2026-10-06 整理;v1.1 增补线上操作许可红线)
> 适用范围:本项目全部前后端开发、数据库变更、构建部署与交付打包。
> 依据:本规范每条约定均从现有代码与部署脚本中提炼,不是理想化模板;示例均可在仓库中找到出处。
> 配套文档:`AGENTS.md`(环境与资源速览)、`README.md`(目录结构与本地开发)。

---

## 1. 总则

1. **环境红线**:服务端 PHP 8.2 + MySQL,禁止替换为其它语言/数据库;代码不得使用 PHP 8.3/8.4 才有的语法(本机 CLI 可能是更高版本,但目标环境是 8.2)。
2. **部署形态**:php-fpm + FTP 上传即生效,**服务端没有任何构建/编译步骤**;一切产物必须在本地构建完成后上传。
3. **数据库配置唯一来源是根目录 `.env`**,缺项或空值必须直接报错(`site/inc/config.php` 的 `qly_fatal_config`),**禁止任何默认值静默回退**。可用 `tools/check_env_guard.php` 验证该行为。
4. **注释写"为什么"**:本项目注释文化是记录坑与原因(如 `devserver.mjs` 解释为何不用 `php -S`、`request.ts` 解释为何 401 要整页重载)。修改代码时沿用此风格,不要写复述代码的注释。
5. **重要功能先出方案,经确认后再动工**;每完成一步主动反馈进度。
6. **默认只做本地,线上与仓库都封停**:①未经用户明确允许,禁止一切线上操作(FTP 上传/覆盖/删除线上文件、线上数据库建表/改表/写入/删除数据);②**仓库不再接收推送**——2026-10-09 用户明确要求「以后不要往仓库里传了」,项目不再 `git push`(如将来用户重新授权,也须逐次单独确认)。用户说「开工」「开始实现」仅授权开发与本地验证(本地 `git commit` 可随时做),**不构成上线或推送授权**。

## 2. 目录结构与职责

| 目录 | 职责 | 进交付包 |
| --- | --- | --- |
| `site/` | 站点根,FTP 上传内容:入口、后端、构建产物、上传文件 | ✅ |
| `site/inc/` | 后端基础设施:config / db / response / auth / notify,**业务代码不得重复实现这些能力** | ✅ |
| `site/api_handlers/` | 各模块接口实现,一个模块一个文件 | ✅ |
| `site/uploads/` | 附件与头像落盘,**部署时永不删除/覆盖** | ❌(线上已有) |
| `frontend/` | Vue 3 工程,`npm run build` 产出 `dist/` | ❌(只上传产物) |
| `frontend/dist_v*`、`dist_revert` 等快照目录 | 历史构建快照,仅排查用 | ❌ |
| `database/init.sql` | 建表 + 种子数据,**数据库结构的唯一事实来源** | ✅ |
| `tools/` | 开发期脚本(建库/自测/迁移/组装/部署),不进交付包 | ❌ |
| `backups/` | 版本备份 zip、删数前的数据备份 SQL,只增不删 | ❌ |
| `.cowork-temp/` | 临时脚本与日志,**任何正式代码不得引用此目录** | ❌ |

`site/.htaccess` 与 `site/.user.ini` 是服务器行为的一部分:缓存策略、SPA 回退、上传上限(64M)、`.env` 禁访问、uploads 禁执行脚本。改这两个文件要像改代码一样谨慎。

## 3. 后端规范(site/)

### 3.1 入口与路由

- 所有接口走唯一入口 `site/api.php`,路由形式 `?r=module/action`,**禁止新增独立 PHP 入口文件**。
- 新接口必须在 `$routes` 表登记一行,同时声明允许的 HTTP 方法、处理文件、处理函数:

```php
'issues/handle' => [['POST'], 'issues.php', 'qly_api_issues_handle'],
```

- 未登记路由 → 404;方法不符 → 405;处理函数缺失 → 500;业务代码抛 `Throwable` → 统一兜底 500。不要在 handler 里自己 echo JSON 逃过这套流程。
- CORS(`Access-Control-Allow-*`)与 OPTIONS 预检已在入口统一处理,handler 不用管。

### 3.2 Handler 编写

- 每个模块一个文件,放 `api_handlers/`,文件内函数命名 `qly_api_<module>_<action>`,文件头 `declare(strict_types=1);`。
- 标准动作顺序:**鉴权 → 取参 → 校验 → 业务 → 写日志 → 响应**。

```php
function qly_api_issues_handle(): void
{
    $user = qly_auth_user();                    // 必须登录(或 qly_admin_user())
    if (!qly_can_handle($user)) { qly_forbidden(); }
    [$title, $desc] = array_values(qly_require(['title' => '标题', 'description' => '描述']));
    // ... 业务(用 qly_insert/qly_update/qly_exec)
    qly_log($user, '问题处理', '问题 ' . $no, $content);
    qly_ok($data);
}
```

- 权限判断用 `inc/auth.php` 现成函数:`qly_has_role`(多角色并集)、`qly_can_handle`、`qly_can_report`、`qly_can_manage_duty`。新增能力判断函数也加在这里,不要散落在 handler 里。
- 输出给前端的实体必须经过 `*_public()` 映射函数(如 `qly_user_public`、`qly_issue_row_public`):**数据库 snake_case → JSON camelCase,且显式挑选字段**,保证 `password_hash`、`token` 等敏感列永远不出现在响应里。

### 3.3 响应与错误码

统一 `{ code, data, message }`,`code !== 0` 即业务错误:

| 场景 | 用法 | code / HTTP |
| --- | --- | --- |
| 成功 | `qly_ok($data)` | 0 / 200 |
| 业务失败 | `qly_fail('xxx不能为空')` | 1 / 200 |
| 未登录 | `qly_unauthorized()` | 401 / 401 |
| 无权限 | `qly_forbidden()` | 403 / 403 |

前端依赖 HTTP 401 触发重新登录、依赖 `code===0` 判定成功,不要发明新的错误约定。

### 3.4 鉴权与会话

- Bearer Token,存 `user_token` 表(**一对多,支持多端同时在线**,互不顶号),TTL 7 天。
- 登录发令牌用 `qly_issue_token()`;重置密码/禁用/删除用户后必须调 `qly_revoke_all_tokens()`。
- 登出只删当前 token(`qly_revoke_token`),不影响其它设备。

### 3.5 角色与数据范围(本项目安全核心)

- 角色是**多值**(`user.roles` 逗号分隔),权限按**并集**计算。角色白名单在两处定义,必须同步改:`inc/auth.php` 的 `qly_roles()` 与前端 `constants/user.ts` 的 `ROLES`。
- 数据可见范围由 `qly_scope_level()` 决定(all / dept / self),列表用 `qly_scope_where()` 拼 SQL,详情逐条校验用 `qly_issue_visible()`——**三者必须同源**,防止"列表看不见、详情却打得开"的越权。
- 新增业务实体的可见范围时,照此模式成对提供"列表 SQL 片段 + 单条校验"两个函数。

### 3.6 数据访问

- 统一走 `inc/db.php`:`qly_all / qly_one / qly_val / qly_exec / qly_insert / qly_update`,全部 PDO 预处理,**禁止字符串拼接 SQL 值**。
- PDO 原生预处理**不允许同名占位符重复**,LIKE 多字段匹配要编号(`:kw1`、`:kw2`),见 `issues.php` 的写法。
- 连接参数已内置优化(先试 `127.0.0.1` 再试 `DB_HOST`、8 秒连接超时、会话时区跟随应用),不要绕过 `qly_db()` 自建连接。
- 事务:跨多表写入时用 `$pdo = qly_db(); $pdo->beginTransaction(); ... commit/rollBack`。

### 3.7 操作日志

- 一切写操作(含登录登出)都要 `qly_log($user, $type, $target, $content)`;日志类型字符串要保持既有命名风格(如 `提交问题`、`问题处理`、`排班维护`),新类型先在 `types/index.ts` 的 `LogType` 里登记。
- 日志失败自动吞异常,不影响主流程;但也因此**不要把业务正确性寄托在日志上**。

### 3.8 上传

- 唯一入口 `api.php?r=upload`;大小限制:应用层 50MB(`qly_app_config`),`.user.ini` 放宽到 64M,改上限要两处同步并确认 nginx `client_max_body_size`。
- 扩展名按场景白名单(头像仅 jpg/jpeg/png;附件白名单见 `upload.php`),图片类要做魔数校验,不只看扩展名。
- 落盘 `uploads/YYYYMM/`,文件名随机化;`uploads/.htaccess` 已禁脚本执行,新增目录不要破坏该保护。

## 4. 前端规范(frontend/)

### 4.1 分层与数据流

```
views ──▶ stores(Pinia) ──▶ api/*.ts ──▶ request.ts(http) ──▶ api.php
```

- **只有 `src/api/` 目录允许发 HTTP 请求**,views 与组件一律通过 store 或直接 import api 模块,禁止直接 import axios。
- api 模块按后端模块一一对应(`issue.ts` ↔ `issues.php`),文件内导出具名函数,返回 `Promise<T>`,`T` 来自 `types/`。

### 4.2 请求层约定(`api/request.ts`)

- 统一走导出的 `http.get/post/put/delete`;需要静默失败(不弹 ElMessage)传 `silent = true`。
- `code !== 0` 会弹错误并 throw;HTTP 401 会 `clearAuthStorage()` 并整页重载到登录页——**清登录态必须连用户缓存一起清**,否则会陷入"守卫放行、接口 401"的死循环(历史教训已写进注释)。
- localStorage 键名固定:`aftersales_token` / `aftersales_user`,不要另起炉灶。

### 4.3 状态管理

- Pinia setup 风格,一个领域一个文件(`stores/` 下 auth / dict / issue / report / siteConfig / user)。
- 跨页面共享的字典、登录态、站点配置进 store;页面私有的临时状态留在组件里,不要什么都塞 store。

### 4.4 路由与权限

- hash 路由;每条路由必须带 `meta.title`,按需 `meta.roles / icon / group / hidden / public`;守卫逻辑在 `router/index.ts`,未登录跳 `/login`,无权限跳 `/403`。
- 页面内元素级权限用 `v-permission="['管理员']"` 指令(默认移除元素,`.disable` 修饰符置灰)。**前端权限只是体验层,服务端必须独立强校验**,两端角色判断逻辑通过 `constants/user.ts` 与 `inc/auth.php` 保持镜像。

### 4.5 类型

- `types/` 全局类型,**禁止 `any`**;枚举用字符串字面量联合(如 `IssueStatus`、`Role`),与后端状态值逐字一致。
- 后端返回 camelCase,由后端 `*_public()` 保证;前端类型定义按 camelCase 书写。

### 4.6 组件与样式

- 通用组件放 `components/`;图表一律走 `components/charts/` 的封装(`BaseChart` + `chartTheme` 统一配色),不要在页面里裸用 ECharts;插画用 `components/illustrations/` 的内联 SVG 组件。
- 颜色、圆角、间距优先用 `styles/theme.css` 的 token,动效用 `animation.css`;新页面不要硬编码色值。
- 业务图标优先 `@icon-park/vue-next`,Element Plus 图标作辅助(已在 `main.ts` 全局注册)。

### 4.7 版本号

- 唯一改动点两处且必须同步:`src/constants/version.ts` 的 `APP_VERSION` 与 `package.json` 的 `version`。
- 递增规则:修 bug / 小改进 → 补丁位 +1;功能类改动 → 次版本 +1。侧边栏展示该版本号,用于确认线上是否已更新。

## 5. 数据库规范

### 5.1 init.sql 规则(照 `AGENTS.md`,逐条执行)

- UTF-8;**不写 `USE`**,不建库删库;无存储过程/触发器/函数。
- 以 `SET NAMES utf8mb4;` 开头,正文用 `START TRANSACTION;` / `COMMIT;` 包住。
- 建表 `CREATE TABLE IF NOT EXISTS`,种子数据 `INSERT ... ON DUPLICATE KEY UPDATE`,**整个脚本必须可重复执行**。
- 统一 `ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci`;每个列写 COMMENT;唯一键 `uk_*`、普通索引 `idx_*`。
- 由 `tools/gen_init_sql.php` 生成,**改表结构时脚本与生成器要同步改**(两处都是事实来源)。

### 5.2 表结构变更流程

1. 写幂等迁移脚本 `tools/migrate_<变更名>.php`(参考 `migrate_category.php`:用 `information_schema` 判断列/索引是否存在,重复执行无副作用);
2. 对线上库执行;
3. **同步更新 `database/init.sql` 与 `tools/gen_init_sql.php`**;
4. 跑 `tools/selftest.php` 验证数据层。

### 5.3 红线与已知教训

- **代码用到的每一张表必须出现在 init.sql 里。** 现存反例:`notification`、`site_config` 两张表线上有、代码在用,但 init.sql 缺失——新库部署会直接缺表。此缺口待修复,修复前打包部署必须手工补建。
- 线上库做 DELETE/UPDATE 前,先用 SELECT 核对影响范围,再导出精确备份(INSERT 格式)到 `backups/`,然后才动手(参考 `backups/v2_notifications_backup.sql` 的做法)。
- 时间列用 `DATETIME`,应用层统一东八区(见 6.4)。

## 6. 构建与部署

### 6.1 本地构建链

```bash
cd frontend
npx vue-tsc --noEmit      # ① 类型检查,任何报错不得部署
npm run build             # ② 单 bundle 构建(inlineDynamicImports,见 vite.config.ts 注释)
node ../tools/assemble.mjs # ③ dist 组装进 site/(会清空 site/assets 再复制)
```

构建是单 JS + 单 CSS:Windows 下的 PHP 内置服务器单线程,多 chunk 会串行排队把页面卡死,**不要改回代码分割**。

### 6.2 FTP 部署流程(参考 `tools/` 旁的 `deploy_v*.py` 系列)

> **红线:每次部署前必须获得用户对该次上线的明确许可**;本地验证通过不等于可以上线。

1. FTPS 连接(`FTP_TLS` + 被动模式),逐文件上传并做 MD5/大小校验;
2. **上传顺序:后端 handler → 新构建产物 → `index.html` 最后**;
3. 全部确认成功后,再删除远端旧 hash 的 JS/CSS;
4. 永不触碰线上 `uploads/`、`.env`、`.user.ini`;
5. 部署后立即冒烟:线上首页 200 + 关键接口 `code=0` + 侧边栏版本号已变。

### 6.3 缓存约定(易踩坑)

- `index.html` 必须 `no-store`(由 `.htaccess` 的 FilesMatch + `index.php` 响应头双重保证)——入口被缓存 = 浏览器一直跑旧 JS,表现为"改了代码没生效"。
- 带 hash 的 `assets/*` 长期缓存 `immutable`,所以**只要 hash 变了浏览器自然会拉新**,不需要手动清缓存。

### 6.4 时区

- 应用统一 `Asia/Shanghai`(`inc/config.php` `date_default_timezone_set` + PDO 会话 `SET time_zone`),服务器时区不同用环境变量 `APP_TIMEZONE` 覆盖。
- 时间落库一律 `'Y-m-d H:i:s'` 字符串 + PHP 侧 `date()`;时区错位的表现是"今日值班人取错日期、时间差 8 小时"。

## 8. 备份与回滚

- 整站备份:`backups/backup_v<版本>_<yyyymmdd>.zip`,大版本变更前必做。
- 数据变更备份:删数/迁移前导出受影响行(INSERT 格式)存 `backups/`,保证可回滚。
- 回滚 = 恢复上一版 zip 中对应文件 + 必要的数据库反向操作;回滚后要清理残留(孤立源文件、旧构建产物、脏数据),并重新跑 `vue-tsc` 与冒烟。

## 9. 交付打包

用户要求"打包应用"时:

1. 把**包内** `.env` 的 4 个数据库值(`DB_HOST/DB_PORT/DB_DATABASE/DB_USERNAME/DB_PASSWORD` 及 `DB_CONNECTION` 保留键名)清空;开发期自加的配置项不带进包;
2. 排除 `config/db.local.php`、`tools/`、`.cowork-temp/`、`backups/`、`frontend/` 源码与快照 dist;
3. 压缩为单个 zip,**包内只有一个顶层目录**;
4. 附上 `database/init.sql`;
5. **不得改动工作目录里的 `.env`**。

## 10. 工作流约定(来自实际事故的教训)

1. **不上线上、不推仓库(默认封停)**:线上部署、回退、线上文件删改、线上库变更一律先单独征得用户同意;仓库推送已由用户明确封停(2026-10-09「以后不要往仓库里传了」),不要再执行 `git push`。开发、本地联调与本地验证随时可做。线上出问题先回退保可用,修复在本地完成验证后等用户确认再上线;线上库只允许业务数据,测试/演示数据用完必须清理。
2. **方案先行**:重要功能先写方案文档(放 `docs/`)等确认,再动工。
3. **删功能要删干净**:下线一个功能,源码、路由、api 模块、构建产物要一起清,并跑 `vue-tsc` 验证——历史教训:回滚后残留的孤立组件让类型检查直接失败。
4. **改完代码必须验证链路完整**:类型检查 → 构建 → 组装 → 本地冒烟,缺一不上传。
5. **新文件必须被引用,快照目录及时清理**:`frontend/dist_v*` 这类快照只用于临时排查,确认稳定后应删除,避免误传上线。
