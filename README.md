# 软件开发管理平台

需求与售后双业务线:「需求提交 → 评审 → 设计 → 开发 → 发布上线」的研发需求闭环,叠加「提交问题 → 售后处理并评级 → 多维统计 → 输出行动建议」的售后闭环。
前端 Vue 3 + TypeScript + Element Plus + Pinia + vue-router + ECharts + xlsx；
后端 PHP 8.2 原生接口 + MySQL，部署走 FTP 上传。

## 本地开发

```bash
# 1. 前端依赖
cd frontend && npm install

# 2. 初始化数据库（会执行 database/init.sql，可重复执行）
php -d extension=pdo_mysql -d extension=mbstring tools/run_sql.php

# 3. 构建前端并组装到站点根
npm run build
node ../tools/assemble.mjs

# 4. 起本地服务（在 site/ 目录下）
php -d extension=pdo_mysql -d extension=mbstring -S 127.0.0.1:8811 -t .
```

访问 `http://127.0.0.1:8811/`。

## 角色与多角色规则

- 角色为**多值**（`user.roles` 逗号分隔），权限与数据范围按**并集**计算。
- 数据可见范围：拥有 销售员 / 售后服务人员 / 管理员 任一角色 → 全部数据；
  仅有 销售经理 → 仅本部门（提交部门 = 本部门）。
- 值班人候选：仅「售后服务人员」角色（启用中账号）。

## 值班排班

- 粒度：**一天一位值班人**，按整月以日历展示。
- 可见性：所有登录用户可查看排班与顶栏「今日值班人」；仅管理员与售后服务人员可维护。
- 维护方式：点击日期改单日（可清除）；「批量排班」从起始日期按周轮值（7 天一轮），可跳过周末，
  连续调用即可排满整月。
- 排班变更写入操作日志（类型「排班维护」）。

### BUG 修复排班（按顺位轮值）

- 位置：值班排班页第二个页签「BUG 修复排班」。
- 粒度：**只排顺序、不排日期**。参与人**直接取自 PingCode 项目成员**（「加入成员」下拉即成员清单），选中即生效，不再和系统账号做姓名匹配。
- 当前顺位记在 `site_config`（键 `bug_duty_cursor`），指向下一个该轮到的人；点「保存顺序」会把顺位置回第 1 位，
  「重置到第 1 顺位」只动游标、不动顺序。
- 顺序表存于 `bug_duty_order`（以 `pingcode_member_id` 为准，唯一键 `uk_bug_duty_member`；`user_id` 为历史字段固定 0）；`duty_schedule`（按日排班）不受影响，两套排班互不干扰。

## 问题同步到 PingCode

- 入口：问题列表「操作」列每行的「同步到 PingCode」（**逐条同步，不支持批量**）。
- 弹窗字段与「开发管理 → 同步任务」完全一致：标题 / 描述 / 优先级 / 负责人 / 状态 / 开始时间 / 结束时间 / 标签。
  默认标题为「【售后问题】问题编号」，描述带出该问题原文；默认状态为「未开始」。
- 权限：开发工程师 / 管理员（与需求同步一致，服务端同样强制校验）。
- 行为：在 PingCode 项目（`PINGCODE_PROJECT_ID`）里创建**「史诗」**工作项，描述下方追加来源信息块；
  默认负责人取 BUG 排班**当前顺位**的人，同步成功后游标往后走一位，轮到末位回到第 1 位。
- 手动改负责人：弹窗里改过负责人（含清空）即视为手动指定，以所选为准且**不消耗顺位**。
- 幂等：`issue.pingcode_task_id` 非空的问题自动跳过，不会重复建单；已同步的在列表里显示工作项编号，可点开跳转。

## 销售分析（输单）

- 菜单：**销售分析**（一级分组，位置在「开发管理」之后、「系统管理」之前），含「输单登记 / 输单列表 / 输单分析」。
- 可见角色：销售员、销售经理、管理员（售后/评审/产品/开发不可见，接口同样 403）。
- 数据范围：**销售员仅本人登记**；**销售经理与管理员为全部**。列表与统计共用 `inc/auth.php` 的
  `qly_lost_scope_where / qly_lost_visible`，避免「列表看不见、详情打得开」。
- 字段（对齐《丢单分析》表格）：客户名称、丢单时间、输单类型、丢单阶段、所属行业、企业规模、
  业务员（自动取登录人，只读）、是否远程演示、最终报价（元）、是否涉及定制化、预算匹配、
  客户最终选择、输单原因描述、部门（自动带入）。
- 字典：新增 5 类，在「系统管理 → 字典管理」维护——
  `loss_type` 输单类型、`loss_stage` 丢单阶段、`industry` 所属行业、`company_scale` 企业规模、`budget_match` 预算匹配。
  停用项不进新表单，历史单据按提交时的名称快照展示。
- 写权限：销售员/销售经理可登记并修改**自己的**单（不能删除）；管理员可修改任意单并删除。
- 表：`lost_order`（字典名做快照，与 `dev_request.module_name` 同一做法）。
  建表脚本：`tools/migrate_lostorder.php`（幂等，建表 + 灌 5 类字典）。
- 客户名称：**要求填写真实的客户企业名称**（placeholder + 字段下方提示），
  **仅提示不拦截**；服务端只校验非空与长度（≤120 字），不按内容拦截，保证历史补录不被挡住。
- 登记页右侧「今天」卡片带天气（天气现象 / 气温 / 最高最低 / 湿度 / 风）：
  服务端代理免费无 key 的 Open-Meteo（`api.php?r=weather/today`），结果缓存 30 分钟；
  城市取环境变量 **`WEATHER_CITY`**（`.env`，当前为 **滕州**，支持县级市，卡片显示「山东滕州」），留空则卡片不显示天气、不影响登记；
  外网不通时自动降级为不显示，不会报错。
- 分析页：顶部按时间段筛选（今日/近 7 天/近 30 天/本月/自定义，默认近 30 天），
  概览 6 张指标卡 + 输单类型 / 丢单阶段 / 所属行业 / 企业规模 / 预算匹配分布 +
  阶段×类型交叉 + 是否远程演示×类型 + 条数与金额趋势 + 业务员/部门/客户排行；
  支持「按单量 / 按金额」切换。口径见每张卡片右上角「?」。

### 同步失败/报「HTTP 0」怎么排查

- `HTTP 0` 不是 PingCode 业务错误，而是**服务端到 `open.pingcode.com` 的请求没拿到响应**
  （连接超时 / 被拒 / TLS 失败）。先确认服务器出网：`curl -sv https://open.pingcode.com/v1/auth/token`
  应返回 400「grant_type 是必填字段」——能返回 400 说明网络与证书都正常，问题在参数或 token。
- 代码侧已做兜底：单个请求与并行请求在传输层失败时都会**自动重试一次**；
  失败时错误信息会带上 curl 原因（如 `Connection timed out`），不再只有 `HTTP 0`。
- 同步弹窗的选项（优先级/状态/成员）缓存 1 小时，且**网络异常时用过期缓存兜底**，
  偶发抖动不会导致弹窗直接打不开。
- token 缓存（`runtime/pingcode_token.json`）对 `expires_in` 做了收敛，异常值不会再产生
  「几十年后过期」的脏缓存；怀疑 token 有问题时直接删掉该文件即可，下次请求会重新换取。

> 交付打包：用户已于 2026-10-28 明确「以后不用打包」，默认不导出 zip；需要时再按 `docs/开发规范.md §9` 执行。

## 部署

前端构建产物与后端代码都在 `site/` 目录下，通过 FTP 上传到站点根即生效，服务器侧无需构建命令。
数据库建表与种子数据由 `database/init.sql` 提供，上传后用站点可访问的方式执行一次即可。

## 时区与缓存（重要）

- **时区**：应用统一使用 `Asia/Shanghai`（`site/inc/config.php` 里 `date_default_timezone_set()`，
  PDO 连接同时执行 `SET time_zone`）。若服务器时区不同，可用环境变量 `APP_TIMEZONE` 覆盖。
  时区错位会导致「今日值班人」取错日期、时间落库错 8 小时。
- **缓存**：`index.html` 必须禁止缓存（`site/index.php` 的响应头 + `site/.htaccess` 的 `FilesMatch`），
  因为 `assets/*` 带内容 hash 可长期缓存，但入口被缓存会让浏览器一直跑旧的 JS，
  表现为「改了代码没生效」。带 hash 的静态产物设为 `immutable` 长期缓存。
